## 系统定位

PMS 是一套面向**网络设备原厂**的实施项目管理系统,服务于"原厂 → 代理商 → 客户"三方协同的设备交付实施全流程。系统管理项目从合同录入到闭环归档的全生命周期,覆盖售前测试、项目执行、转包代施、客户回访、维保跟踪、技术公告等业务场景。

**三方关系**:
- **原厂(系统主方)**:服务经理(SM,区域负责人,统筹区域项目进度)、项目经理(PM)、工程管理部(EM)、管理员、主任
- **代理商/服务商**:承接原厂转包的实施工作,作为外部执行方
- **客户**:设备最终用户,接收交付并参与验收签核

**两种执行模式**:
- **自施**:PM → 自有工程师 → 客户现场
- **代施(转包)**:PM → 代理商 → 代理商工程师 → 客户现场

## Clarifications

### Session 2026-07-09

- Q: 服务经理(SM)的角色定位是什么? → A: 服务经理是区域负责人角色,负责统筹区域的项目进度

> 澄明:服务经理(SM)在系统中承担区域负责人职责,核心职能为统筹其所负责区域内的项目进度。此定义适用于所有涉及 SM 的业务流程(项目指派、售前审批、回退流程等)。

- Q: 新系统的终端覆盖范围是什么? → A: 全端覆盖 —— PC Web + 工程师移动端 H5 + 代理商/客户 H5 入口

> 澄明:新系统 MUST 支持三类终端:(1) PC Web 管理后台(全功能,面向内部用户);(2) 工程师移动端 H5(现场作业:签到/拍照/进度上报/异常上报,面向自有工程师与代理商工程师);(3) 代理商/客户 H5 入口(进度查看/审批/签核/文档下载,轻量级外部交互)。此决策影响架构分层、接口设计与任务分解。

- Q: 数据迁移策略是什么? → A: 仅迁移核心业务表(项目/售前/转包/回访/维保),非核心表不迁移

> 澄明:数据迁移范围限定为核心业务表 —— 项目(pm_project*)、售前(pm_presales*)、转包(pm_subcontract*)、回访(pm_cl*)、维保(pm_project_maintenance*)及关联的基础数据(fnd_*)与用户/部门数据。非核心表(临时表如 temp_project_warranty_state、日志表、历史冗余表)不迁移。迁移方案(ETL 工具、字段映射、校验机制)在 plan 阶段细化。

- Q: 新系统的并发用户与核心性能目标是多少? → A: 1000 并发用户,报表 P95 ≤2 秒

> 澄明:新系统 MUST 支持 1000 并发用户无性能 degradation(适配全端覆盖后的用户基数扩大)。核心报表查询响应时间 P95 ≤2 秒(百万级数据量)。此目标影响架构分层、缓存策略与压测验收标准。

- Q: 新系统对老工作流(Activiti + BPMN)的处理策略? → A: 保留业务流程语义,引擎与流程定义重新实现

> 澄明:新系统 MUST 保留老系统的业务流程语义(售前审批、转包多级审批、回访审批、闭环流程的状态机、审批节点、角色指派规则),但 MUST NOT 直接复用 Activiti 5.x 引擎与原 BPMN 文件。新系统 MUST 选用现代工作流引擎重新实现流程定义。具体引擎选型在 plan 阶段决定。此决策避免遗留技术债,同时保证业务连续性。

- Q: 新系统与 SPMS 备件系统的关联策略? → A: 通过标准接口集成(解耦,不共享数据库)

> 澄明:新 PMS 与 SPMS MUST 解耦,不再共享 dppms_d365 数据库。备件领用/归还/返修/替换等与设备资产流转相关的操作 MUST 通过标准 API 接口交互。此决策为新系统独立演进与 SPMS 后续升级预留空间,同时保持业务数据一致性。

- Q: 售前测试的定位与项目管理的业务场景适配机制? → A: 售前测试是正式合同确定前的项目测试环境跟踪,可像标准项目一样管理但仅关注售前业务环境;项目管理需针对不同业务场景支持不同里程碑和交付环节

> 澄明:
> 1. **售前测试定位**:售前测试是正式合同确定前的项目测试环境跟踪,业务上可像标准项目一样管理(状态机/审批流/成员/交付件),但范围仅限售前测试的业务环境(不包含合同执行/付款/验收等后续环节)。
> 2. **项目管理业务场景适配**:项目管理 MUST 支持多业务场景模板,不同业务场景(标准实施/售前测试/转包代施/维保等)MUST 可配置不同的里程碑节点与交付环节。系统 MUST 提供业务场景模板机制,而非硬编码单一流程。

- Q: 业务场景模板与项目类型的关系? → A: 正交维度(项目类型 × 业务场景模板,灵活组合)

> 澄明:项目类型(售后 10/售前 20/非业务 30/自定义 40)与业务场景模板(标准实施/售前测试/转包代施/维保)为正交维度,非 1:1 映射。一个项目类型可对应多个业务场景(如"售前 20"类型可对应"售前测试"或"售前维保"场景)。系统 MUST 支持二维组合配置,数据模型 MUST 同时记录项目类型与业务场景模板标识。

- Q: 项目管理功能增强——主子项目层级拆分机制? → A: 大型全国项目可拆分为多个小项目交由不同区域团队实施,有明确主子项目层级划分与权限管控

> 澄明:
> 1. **主子项目层级**:系统 MUST 支持项目层级拆分,一个主项目(如全国项目)MUST 可拆分为多个子项目(区域项目),子项目 MUST 可独立实施但归属主项目统辖。
> 2. **权限管控**:主项目与子项目 MUST 有明确的权限隔离——区域团队仅可见/操作本区域的子项目,主项目管理员(如总部 PM)MUST 可查看全部子项目的汇总进度。
> 3. **数据汇总**:主项目 MUST 能汇总子项目的进度、里程碑、交付件、成员负荷等数据,支持层级报表。
> 4. **状态联动**:主项目闭环 MUST 以全部子项目闭环为前置条件(主项目不可先于子项目闭环)。
> 此为老系统的功能增强(老系统无此能力),标注 `[推断]`。

- Q: 里程碑与交付环节的配置方式? → A: 预置标准模板 + 管理员可扩展(预置 4 种 + 支持新增/调整)

> 澄明:系统 MUST 预置 4 种标准业务场景模板(标准实施/售前测试/转包代施/维保),每个模板含默认里程碑节点与交付环节。管理员 MUST 可基于预置模板派生新模板、调整里程碑节点、增删交付环节。模板 MUST 支持版本管理,项目实例创建时绑定模板版本快照(避免后续模板变更影响已创建项目)。

- Q: 主子项目拆分后转包/回访/维保的归属层级? → A: 归属子项目,主项目可汇总

> 澄明:子项目为业务执行单元,转包、回访、维保等下游业务模块 MUST 归属子项目(因执行发生在区域)。主项目 MUST 可汇总查看全部子项目的转包/回访/维保数据,保持统辖可见性。具体规则:
> 1. **转包**:子项目独立发起转包审批,主项目汇总全部子项目的转包金额与执行状态
> 2. **回访**:回访按子项目发起,主项目闭环前 MUST 确认全部子项目回访已完成
> 3. **维保**:维保记录归属子项目,主项目可按子项目维度汇总维保统计

### 信心等级标注规则(宪法 v2.0.0 原则 III 合规)

本 spec 的每条 FR/SC 按以下规则标注信心等级:

- `[确定]`:老系统代码/知识库中已验证的行为,可直接追溯至源文件
- `[推断]`:基于部分代码或文档证据推断,需 plan 阶段验证
- `[猜测]`:无直接证据,基于行业惯例推测

**默认规则**:未显式标注的 FR/SC 默认为 `[确定]`(因本 spec 基于老系统逆向工程,绝大多数行为已在代码中验证)。仅在偏离老系统行为、属于新系统目标设定、或无直接证据时显式标注 `[推断]` 或 `[猜测]`。

**关键标注清单**(仅列出非默认等级的 FR/SC):

| FR/SC | 等级 | 理由 |
|-------|------|------|
| FR-058~060 | `[确定]`(现状)+ `[推断]`(目标) | 老系统 Activiti 5.23.0 已验证 `[确定]`;新系统"现代引擎重新实现"为目标设定 `[推断]` |

| SC-015 | `[推断]` | 技术公告匹配准确率 ≥95% 为目标设定 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 项目全生命周期管理 (Priority: P1)

作为项目经理(PM),我需要从合同录入开始管理项目,经过服务经理指派、PM 指派、实施跟踪,直到项目闭环,以便管控项目从立项到交付的完整流程。对于大型全国项目,我需要将其拆分为多个区域子项目,交由不同区域团队并行实施,并统辖全部子项目进度。

**Why this priority**:项目管理是系统的核心业务主干,PMS-struts 模块 60+ 功能点均围绕此流程展开,是其他所有业务模块的基础。主子项目层级拆分是全国性项目实施的必要增强能力。

**Independent Test**:可独立测试——给定一个合同号,能完成"创建项目(状态30)→ 指定SM(状态31)→ 指定PM(状态32)→ 进入实施(状态40)→ 闭环(状态100)"的完整流转;且给定一个主项目,能拆分为多个子项目,各子项目独立实施后主项目方可闭环。

**Acceptance Scenarios**:

1. **Given** 一个已签订的合同号, **When** 用户录入合同号并创建项目, **Then** 系统创建项目记录,状态置为"30 已创建",项目信息主表生成一条记录
2. **Given** 项目处于"30 已创建"状态, **When** 管理员指定服务经理(SM), **Then** 项目状态流转为"31 待指派PM",SM 收到通知
3. **Given** 项目处于"31"状态, **When** SM 指定项目经理(PM), **Then** 项目状态流转为"32 已指派PM",PM 收到通知
4. **Given** 项目处于"32"状态, **When** PM 启动实施, **Then** 项目状态流转为"40 实施中"
5. **Given** 项目处于"40 实施中", **When** PM 发起闭环申请并通过审批, **Then** 项目状态流转为"100 已闭环"
6. **Given** 项目处于任意实施阶段, **When** PM 申请回退, **Then** 项目按回退路径流转(36 SM回退 / 38 PM回退至服务经理 / 42 PM回退实施)
7. **Given** 项目处于"30"或"31"状态, **When** 用户标记"不予跟踪", **Then** 项目状态流转为"20 不予跟踪"(终态)

### User Story 2 - 售前测试管理 (Priority: P1)

作为服务经理(SM),我需要发起售前测试申请,经过 SM 审批、PM 跟踪、工程管理部回访,最终闭环,以便在正式合同确定前完成项目测试环境的跟踪与验证。

**Why this priority**:售前测试是正式合同确定前的项目测试环境跟踪,业务上可像标准项目一样管理(状态机/审批流/成员/交付件),但范围仅限售前测试业务环境。测试通过后才可闭环,直接影响后续正式项目立项。

**Independent Test**:可独立测试——给定一个售前测试申请,能完成"申请(10)→ SM审批指定PM(31)→ PM跟踪(32/33)→ EM回访(100闭环)"的完整流程。

**Acceptance Scenarios**:

1. **Given** 申请人发起售前测试申请, **When** 提交申请, **Then** 系统启动工作流,状态置为"31 待服务经理指定PM"
2. **Given** 售前测试处于"31"状态, **When** SM 审批通过并指定 PM, **Then** 状态流转为"32 已指定PM,待PM跟踪"
3. **Given** 售前测试处于"32"状态, **When** PM 完成跟踪, **Then** 状态流转为"33 PM已跟踪,待工程管理部回访"
4. **Given** 售前测试处于"33"状态, **When** 工程管理部(EM)回访通过, **Then** 状态流转为"100 已闭环"
5. **Given** 售前测试处于任意非闭环状态, **When** 用户终止或驳回, **Then** 状态流转为"20 已终止/已驳回"(终态)
6. **Given** SM 审批未通过, **When** SM 退回修改, **Then** 退回至申请人修改后重新提交

### User Story 3 - 项目转包(代施)管理 (Priority: P1)

作为项目经理(PM),我需要将项目部分工作转包给代理商/服务商,经过多级审批、合同执行、付款、回访、验收,以便通过外部执行方完成项目交付。

**Why this priority**:转包是代施模式的核心,涉及 50+ 功能点,且与 D365 采购订单、发票识别等外部系统深度集成,是代理商管理业务的主干。

**Independent Test**:可独立测试——给定一个转包申请,能完成"创建(草稿)→ 发起申请 → 多级审批 → 合同执行 → 付款 → 回访 → 验收"的完整流程。

**Acceptance Scenarios**:

1. **Given** PM 选择项目并创建转包, **When** 保存转包信息, **Then** 系统生成转包项目主表记录,状态为"0 草稿"
2. **Given** 转包处于草稿状态, **When** PM 发起申请, **Then** 启动多级审批流(受益部门服务经理 → 通用审批节点 → 工程管理部 → 主任)
3. **Given** 转包审批通过, **When** 进入合同执行, **Then** 系统向 D365 推送采购订单,并跟踪采购收货
4. **Given** 转包合同执行中, **When** 代理商提交付款申请, **Then** 系统识别发票并启动付款审批流
5. **Given** 转包合同执行完成, **When** 发起回访, **Then** 系统生成回访问卷并进入回访审批
6. **Given** 转包回访通过, **When** 进入验收, **Then** 系统记录验收结果并闭环

---

### User Story 4 - 项目回访与闭环管理 (Priority: P2)

作为工程管理部(EM)人员,我需要对已交付项目发起回访,通过问卷填写与审批完成项目闭环,以便收集客户反馈并正式关闭项目。

**Why this priority**:回访是项目闭环流程的关键环节,直接影响项目状态从"40 实施中"到"100 已闭环"的流转。

**Independent Test**:可独立测试——给定一个已完成实施的项目,能完成"发起回访 → 审批 → 填写问卷 → 通过/驳回"的完整流程。

**Acceptance Scenarios**:

1. **Given** 项目实施完成, **When** EM 发起回访申请, **Then** 系统启动回访工作流
2. **Given** 回访工作流启动, **When** 回访审批人审批, **Then** 系统记录审批意见(通过/退回)
3. **Given** 回访审批通过, **When** 填写回访问卷, **Then** 系统保存问卷结果并计算评分
4. **Given** 回访问卷提交, **When** 审批通过, **Then** 项目闭环流程状态回到"10",项目可正式闭环
5. **Given** 回访被驳回, **When** 申请人重新提交, **Then** 系统重新进入审批环节

### User Story 5 - 维保记录管理 (Priority: P2)

作为项目经理(PM),我需要为已交付项目创建维护记录,填写维护问卷并上传交付件,以便跟踪售后维保服务质量。

**Why this priority**:维保管理覆盖售后项目、售前项目、非业务类、自定义 4 种类型,是项目交付后的长期跟踪机制。

**Independent Test**:可独立测试——给定一个已交付项目,能完成"创建维护记录 → 填写问卷 → 上传交付件 → 保存"的完整流程。

**Acceptance Scenarios**:

1. **Given** 用户进入维护记录列表, **When** 创建维护记录, **Then** 系统根据 projectType(10售后/20售前/30非业务/40自定义)关联对应项目主表
2. **Given** 维护记录已创建, **When** 用户填写维护问卷, **Then** 系统保存问卷结果(头表 + 行表)
3. **Given** 维护记录问卷已填, **When** 用户上传交付件, **Then** 系统记录交付件明细
4. **Given** 维护记录完整, **When** 用户保存, **Then** 系统持久化维护记录并更新服务交付统计

### Edge Cases

- **项目状态非法流转**:当用户尝试从"100 已闭环"直接流转到"40 实施中"时,系统 MUST 拒绝并提示合法流转路径
- **售前测试超期未闭环**:当售前测试在"33 待回访"状态停留超过约定时长,系统 MUST 触发超期提醒
- **转包审批超时**:当转包审批在某一节点停留超时,系统 MUST 自动升级通知上级
- **回访问卷缺失**:当回访申请已发起但问卷未填写,系统 MUST 阻止审批通过
- **技术公告影响范围匹配失败**:当软件版本无法匹配到任何项目时,系统 MUST 提示"无受影响项目"并允许手动指定
- **项目成员批量变更冲突**:当批量变更项目成员时遇到并发修改,系统 MUST 提示冲突并要求刷新重试
- **合同合并拆分数据不一致**:当合并/拆分合同导致设备清单与合同关联断裂时,系统 MUST 校验并阻止操作
- **D365 接口不可用**:当推送采购订单到 D365 失败时,系统 MUST 记录失败日志并支持重试,不阻塞转包业务流程
- **文件上传中断**:当大文件上传过程中网络中断,系统 MUST 支持断点续传或重新上传
- **多数据源切换异常**:当跨数据源查询(如同时查 dppms_d365 与 D365)时某一数据源不可用,系统 MUST 降级提示而非整体崩溃
- **主项目提前闭环**:当主项目存在未闭环子项目时,系统 MUST 拒绝主项目闭环申请并提示未闭环子项目清单
- **子项目权限越界**:当区域团队尝试访问非本区域子项目时,系统 MUST 拒绝并记录安全日志
- **项目拆分后成员归属冲突**:当主项目拆分子项目时,系统 MUST 校验成员归属(同一成员不可同时归属多个并行子项目,除非显式授权)

- **目标用户**:原厂内部人员(管理员、服务经理、项目经理、工程管理部、主任)、代理商/服务商、客户(通过 H5 入口)

- **外部系统可用性**:D365/SMS/OA/EHR/CRM 等外部系统保持稳定,接口可用性 ≥99%
- **CAS 单点登录**:沿用现有 CAS 认证体系,不重新构建认证中心
- **多数据源**:老系统的多数据源架构需在新系统中保留,不可合并为单库
- **工作流引擎**:新系统 MUST 保留老系统业务流程语义(状态机、审批节点、角色指派),但 MUST NOT 复用 Activiti 5.x 引擎与原 BPMN 文件;MUST 选用现代工作流引擎重新实现流程定义(具体选型在 plan 阶段决定)
- **移动端支持**:新系统 MUST 全端覆盖 —— PC Web(全功能)+ 工程师移动端 H5(现场作业)+ 代理商/客户 H5 入口(轻量级外部交互)
- **报表导出**:Excel 导出为基本需求,PDF 导出可选
- **集成方式**:与 D365 的 OAuth2 + REST API 集成模式需保留
- **SPMS 关联**:新 PMS 与 SPMS MUST 解耦,不共享数据库,备件相关操作通过标准 API 接口集成
- **实体类名映射(L2)**:spec 的 16 个核心实体仅列中文名,具体实体类名(如 Project/Presales/SubcontractProject 等)与数据库表的映射在 plan 阶段补充

## 范围边界

### 模块维度说明(L1 澄清)

> spec 的"9 个业务模块"按**业务功能**维度划分(售前/转包/维保等),老系统代码的"8 个 Maven 子模块"按**技术分层**维度划分(pms-struts/core/pms-activiti 等)。二者维度不同,映射关系如下:

| spec 业务模块 | 对应代码模块 | 说明 |
|--------------|-------------|------|
| 项目管理、售前、转包、闭环回访、维保、技术公告、周报文件、报表 | pms-struts | 主业务模块,含全部 Action/Service |
| 系统管理 | core | 用户/角色/菜单/权限 |
| 工作流引擎(横切) | pms-activiti | Activiti 封装 |
| (横切)springmvc 扩展 | pms-springmvc | DispatchProject/PmSynchronize/D365DataJob |
| (横切)D365 集成 | pms-ext-d365 | OAuth2+REST API |
| (横切)安全防护 | pms-security | XSS/CSRF/SQL 注入(FR-080~083) |
| (横切)发票集成 | pms-ext-fp | FP 平台集成(FR-084~085) |
| (横切)规则引擎 | pms-rules | Aviator+LiteFlow(FR-086~088) |

### 范围内

- PMS 主系统的所有业务模块(项目管理、售前、转包、闭环、回访、维保、技术公告、周报、系统管理、报表、工作流)
- 与外部系统(D365/SMS/OA/EHR/CRM/SAP/MES)的集成接口
- 多数据源架构与数据隔离
- 文件上传下载与存储
- CAS 单点登录集成
- 数据权限与角色权限体系

### 范围外

- SPMS 备件管理系统的功能(共用数据库但独立系统)
- 具体技术栈选型(框架、数据库、缓存等)
- 新系统的部署架构
- 新系统的 UI/UX 设计细节
- 数据迁移方案(ETL 工具选型、字段映射规则、校验机制在 plan 阶段细化,本 spec 仅定义迁移范围:核心业务表 + 基础数据)
- 性能压测具体指标(另行规划)
