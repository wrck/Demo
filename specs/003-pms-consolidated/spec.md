## 系统定位

PMS 是一套面向**网络设备原厂**的实施项目管理系统，服务于"原厂 → 代理商 → 客户"三方协同的设备交付实施全流程。系统管理项目从合同录入到闭环归档的全生命周期，覆盖售前测试、项目执行、转包代施、客户回访、维保跟踪、技术公告等业务场景。

**三方关系**:
- **原厂(系统主方)**：服务经理(SM,区域负责人,统筹区域项目进度)、项目经理(PM)、工程管理部(EM)、管理员、主任
- **代理商/服务商**：承接原厂转包的实施工作,作为外部执行方
- **客户**：设备最终用户,接收交付并参与验收签核

**两种执行模式**:
- **自施**：PM → 自有工程师 → 客户现场
- **代施(转包)**：PM → 代理商 → 代理商工程师 → 客户现场

## Clarifications

### Session 2026-07-09（合并自 001 与 002）

#### 来自 003（合并 spec 澄清）

- Q: 项目阶段模型如何统一（001 的 8 阶段交付模型 vs 002 的项目状态码）？ → A: 双层并行模型。002 的状态码（30 已创建/31 待指派PM/32 已指派PM/40 实施中/100 已闭环/20 不予跟踪）作为项目生命周期顶层状态机（立项→指派→实施→闭环）；001 的 8 阶段（未开始/工前准备/编写实施方案/制定施工计划/实施部署/验收交维/超期）作为"40 实施中"状态内的交付子阶段。两套模型分层并行，既保留老系统状态机语义，又支撑新系统交付阶段跟踪。
- Q: 系统自身可用性目标（SLA）是什么？ → A: 99.9% 全天候，全年 7×24 可用性 ≥99.9%（年停机 ≤8.76 小时）；割接管理窗口期（通常夜间）系统 MUST 可用以支撑割接执行；数据归档与冷存储取回可异步处理不阻塞核心业务。
- Q: 001 新增模块与 002 老模块如何统一组织？ → A: 按业务域聚合。以"项目交付生命周期"为主线组织模块（立项/工前/计划/方案/部署/验收/割接/归档），002 老模块作为子能力嵌入对应阶段（转包嵌入"部署"、回访嵌入"验收"、维保嵌入"归档"、售前作为独立业务场景复用生命周期），横切模块（系统管理/工作流/报表/集成/安全/数据持久化）独立。符合领域驱动设计原则，模块边界清晰。
- Q: 新老系统切换方式是什么？ → A: 并行运行+增量同步+灰度切换。新老系统并行运行一段时间，增量数据双向同步，按办事处或项目类型灰度切换，切换失败可回滚至老系统。
- Q: 移动端离线缓存范围是什么？ → A: 限定只读数据+现场采集离线。离线缓存范围限定为只读参考数据（项目信息/设备清单/实施方案）与现场采集类数据（施工照片/工勘表单/配置 Log/签到记录），联网后自动同步；审批/状态变更等写操作 MUST 联机执行，离线时禁用。

#### 来自 001（新系统业务补充澄清）

- Q: 工前准备中的"用户"指什么角色？数据来源何处？ → A: 指项目交付环境实际使用设备的最终用户（可能是直签客户或非直签代理商实施的设备使用用户），并非使用本系统的用户；项目实施角度归纳为"客户"；客户基础信息与默认联系人由外部 CRM 带入，在本系统中维护更新。
- Q: 项目阶段（8 阶段）如何推进与回退？ → A: 自动推进为主、关键节点人工触发；系统依据各阶段交付件完成情况自动判定阶段完成，割接上线、验收等关键节点需人工触发；支持受控回退（需审批）。
- Q: 多角色并发编辑同一项目数据的冲突如何处理？ → A: 乐观锁+字段级合并；默认乐观并发，保存时版本不一致则提示冲突字段并支持字段级合并；已提交审核的施工计划/实施方案等文档锁定不可编辑。
- Q: 系统的认证与权限模型是什么？ → A: LDAP/AD 集成统一认证，RBAC 角色权限+数据权限；按"办事处/项目归属"维度过滤数据（如项目经理仅见自己项目，交付管理人员见全局）。
- Q: 交付件/配置 Log/巡检/割接归档/AI 训练数据的保留期限与归档策略？ → A: 分级保留：交付件与配置 Log 随项目归档保留 ≥ 5 年（合同质保与审计需要），巡检报告与割接归档 ≥ 3 年，AI 排障训练数据脱敏后长期保留；超期自动归档至冷存储（对象存储低频访问层）。

#### 来自 002（老系统逆向澄清）

- Q: 服务经理(SM)的角色定位是什么? → A: 服务经理是区域负责人角色,负责统筹区域的项目进度。
- Q: 新系统的终端覆盖范围是什么? → A: 全端覆盖 —— PC Web + 工程师移动端 H5 + 代理商/客户 H5 入口。
- Q: 数据迁移策略是什么? → A: 仅迁移核心业务表(项目/售前/转包/回访/维保),非核心表不迁移。
- Q: 新系统的并发用户与核心性能目标是多少? → A: 1000 并发用户,报表 P95 ≤2 秒。
- Q: 新系统对老工作流(Activiti + BPMN)的处理策略? → A: 保留业务流程语义,引擎与流程定义重新实现（不复用 Activiti 5.x 引擎与原 BPMN 文件）。
- Q: 新系统与 SPMS 备件系统的关联策略? → A: 通过标准接口集成(解耦,不共享数据库)。
- Q: 售前测试的定位与项目管理的业务场景适配机制? → A: 售前测试是正式合同确定前的项目测试环境跟踪,可像标准项目一样管理但仅关注售前业务环境；项目管理需针对不同业务场景支持不同里程碑和交付环节。
- Q: 业务场景模板与项目类型的关系? → A: 正交维度(项目类型 × 业务场景模板,灵活组合)。
- Q: 项目管理功能增强——主子项目层级拆分机制? → A: 大型全国项目可拆分为多个小项目交由不同区域团队实施,有明确主子项目层级划分与权限管控。
- Q: 里程碑与交付环节的配置方式? → A: 预置标准模板 + 管理员可扩展(预置 4 种 + 支持新增/调整)。
- Q: 主子项目拆分后转包/回访/维保的归属层级? → A: 归属子项目,主项目可汇总。

### 信心等级标注规则（来自 002）

本 spec 的每条 FR/SC 按以下规则标注信心等级：
- `[确定]`：老系统代码/知识库中已验证的行为,可直接追溯至源文件
- `[推断]`：基于部分代码或文档证据推断,需 plan 阶段验证
- `[猜测]`：无直接证据,基于行业惯例推测

**默认规则**：未显式标注的 FR/SC 默认为 `[确定]`。仅在偏离老系统行为、属于新系统目标设定、或无直接证据时显式标注 `[推断]` 或 `[猜测]`。

### User Story 1 - 项目全生命周期管理 (Priority: P1) `[来源: 002]`

作为项目经理(PM),我需要从合同录入开始管理项目,经过服务经理指派、PM 指派、实施跟踪,直到项目闭环,以便管控项目从立项到交付的完整流程。对于大型全国项目,我需要将其拆分为多个区域子项目,交由不同区域团队并行实施,并统辖全部子项目进度。

**Why this priority**: 项目管理是系统的核心业务主干,PMS-struts 模块 60+ 功能点均围绕此流程展开,是其他所有业务模块的基础。主子项目层级拆分是全国性项目实施的必要增强能力。

**Independent Test**: 可独立测试——给定一个合同号,能完成"创建项目(状态30)→ 指定SM(状态31)→ 指定PM(状态32)→ 进入实施(状态40)→ 闭环(状态100)"的完整流转；且给定一个主项目,能拆分为多个子项目,各子项目独立实施后主项目方可闭环。

**Acceptance Scenarios**:

1. **Given** 一个已签订的合同号, **When** 用户录入合同号并创建项目, **Then** 系统创建项目记录,状态置为"30 已创建",项目信息主表生成一条记录
2. **Given** 项目处于"30 已创建"状态, **When** 管理员指定服务经理(SM), **Then** 项目状态流转为"31 待指派PM",SM 收到通知
3. **Given** 项目处于"31"状态, **When** SM 指定项目经理(PM), **Then** 项目状态流转为"32 已指派PM",PM 收到通知
4. **Given** 项目处于"32"状态, **When** PM 启动实施, **Then** 项目状态流转为"40 实施中"
5. **Given** 项目处于"40 实施中", **When** PM 发起闭环申请并通过审批, **Then** 项目状态流转为"100 已闭环"
6. **Given** 项目处于任意实施阶段, **When** PM 申请回退, **Then** 项目按回退路径流转(36 SM回退 / 38 PM回退至服务经理 / 42 PM回退实施)
7. **Given** 项目处于"30"或"31"状态, **When** 用户标记"不予跟踪", **Then** 项目状态流转为"20 不予跟踪"(终态)
8. **Given** 一个主项目, **When** PM 拆分为多个子项目, **Then** 各子项目独立实施,主项目闭环 MUST 以全部子项目闭环为前置条件 `[推断]`

### User Story 2 - 售前测试管理 (Priority: P1) `[来源: 002]`

作为服务经理(SM),我需要发起售前测试申请,经过 SM 审批、PM 跟踪、工程管理部回访,最终闭环,以便在正式合同确定前完成项目测试环境的跟踪与验证。售前测试设备发货后系统自动获取首次临时授权 `[来源: 001]`,实现售前测试零等待授权。

**Why this priority**: 售前测试是正式合同确定前的项目测试环境跟踪,业务上可像标准项目一样管理,但范围仅限售前测试业务环境。测试通过后才可闭环,直接影响后续正式项目立项。

**Independent Test**: 可独立测试——给定一个售前测试申请,能完成"申请(10)→ SM审批指定PM(31)→ PM跟踪(32/33)→ EM回访(100闭环)"的完整流程；设备发货后首次临时授权自动获取。

**Acceptance Scenarios**:

1. **Given** 申请人发起售前测试申请, **When** 提交申请, **Then** 系统启动工作流,状态置为"31 待服务经理指定PM"
2. **Given** 售前测试处于"31"状态, **When** SM 审批通过并指定 PM, **Then** 状态流转为"32 已指定PM,待PM跟踪"
3. **Given** 售前测试处于"32"状态, **When** PM 完成跟踪, **Then** 状态流转为"33 PM已跟踪,待工程管理部回访"
4. **Given** 售前测试处于"33"状态, **When** 工程管理部(EM)回访通过, **Then** 状态流转为"100 已闭环"
5. **Given** 售前测试处于任意非闭环状态, **When** 用户终止或驳回, **Then** 状态流转为"20 已终止/已驳回"(终态)
6. **Given** 售前测试设备已发货 `[来源: 001]`, **When** 系统检测到发货状态, **Then** 自动获取首次临时授权并下发至设备,可立即用于测试

### User Story 3 - 项目转包(代施)管理 (Priority: P1) `[来源: 002]`

作为项目经理(PM),我需要将项目部分工作转包给代理商/服务商,经过多级审批、合同执行、付款、回访、验收,以便通过外部执行方完成项目交付。

**Why this priority**: 转包是代施模式的核心,涉及 50+ 功能点,且与 D365 采购订单、发票识别等外部系统深度集成,是代理商管理业务的主干。

**Independent Test**: 可独立测试——给定一个转包申请,能完成"创建(草稿)→ 发起申请 → 多级审批 → 合同执行 → 付款 → 回访 → 验收"的完整流程。

**Acceptance Scenarios**:

1. **Given** PM 选择项目并创建转包, **When** 保存转包信息, **Then** 系统生成转包项目主表记录,状态为"0 草稿"
2. **Given** 转包处于草稿状态, **When** PM 发起申请, **Then** 启动多级审批流(受益部门服务经理 → 通用审批节点 → 工程管理部 → 主任)
3. **Given** 转包审批通过, **When** 进入合同执行, **Then** 系统向 D365 推送采购订单,并跟踪采购收货
4. **Given** 转包合同执行中, **When** 代理商提交付款申请, **Then** 系统识别发票并启动付款审批流
5. **Given** 转包合同执行完成, **When** 发起回访, **Then** 系统生成回访问卷并进入回访审批
6. **Given** 转包回访通过, **When** 进入验收, **Then** 系统记录验收结果并闭环

### User Story 4 - 项目回访与闭环管理 (Priority: P2) `[来源: 002]`

作为工程管理部(EM)人员,我需要对已交付项目发起回访,通过问卷填写与审批完成项目闭环,以便收集客户反馈并正式关闭项目。

**Why this priority**: 回访是项目闭环流程的关键环节,直接影响项目状态从"40 实施中"到"100 已闭环"的流转。

**Independent Test**: 可独立测试——给定一个已完成实施的项目,能完成"发起回访 → 审批 → 填写问卷 → 通过/驳回"的完整流程。

**Acceptance Scenarios**:

1. **Given** 项目实施完成, **When** EM 发起回访申请, **Then** 系统启动回访工作流
2. **Given** 回访工作流启动, **When** 回访审批人审批, **Then** 系统记录审批意见(通过/退回)
3. **Given** 回访审批通过, **When** 填写回访问卷, **Then** 系统保存问卷结果并计算评分
4. **Given** 回访问卷提交, **When** 审批通过, **Then** 项目闭环流程状态回到"10",项目可正式闭环
5. **Given** 回访被驳回, **When** 申请人重新提交, **Then** 系统重新进入审批环节

### User Story 5 - 维保记录管理 (Priority: P2) `[来源: 002]`

作为项目经理(PM),我需要为已交付项目创建维护记录,填写维护问卷并上传交付件,以便跟踪售后维保服务质量。

**Why this priority**: 维保管理覆盖售后项目、售前项目、非业务类、自定义 4 种类型,是项目交付后的长期跟踪机制。

**Independent Test**: 可独立测试——给定一个已交付项目,能完成"创建维护记录 → 填写问卷 → 上传交付件 → 保存"的完整流程。

**Acceptance Scenarios**:

1. **Given** 用户进入维护记录列表, **When** 创建维护记录, **Then** 系统根据 projectType(10售后/20售前/30非业务/40自定义)关联对应项目主表
2. **Given** 维护记录已创建, **When** 用户填写维护问卷, **Then** 系统保存问卷结果(头表 + 行表)
3. **Given** 维护记录问卷已填, **When** 用户上传交付件, **Then** 系统记录交付件明细
4. **Given** 维护记录完整, **When** 用户保存, **Then** 系统持久化维护记录并更新服务交付统计

### User Story 6 - 技术公告与修复任务管理 (Priority: P2) `[来源: 002, 增强: 001]`

作为管理员,我需要发布技术公告,审批后发布修复任务,跟踪受影响项目的修复进展,以便管控产品技术问题的修复闭环。割接已知隐患自动匹配技术公告 `[来源: 001]`,ITR 故障关联技术公告编号 `[来源: 001]`。

**Why this priority**: 技术公告涉及软件版本影响范围匹配、受影响项目检索、修复任务周报,是产品技术问题跟踪的核心模块。

**Independent Test**: 可独立测试——给定一个技术公告,能完成"创建 → 审批 → 发布修复任务 → 跟踪 → 闭环"的完整流程。

### Edge Cases

#### 来自 002（历史系统）

- **项目状态非法流转**：当用户尝试从"100 已闭环"直接流转到"40 实施中"时,系统 MUST 拒绝并提示合法流转路径
- **售前测试超期未闭环**：当售前测试在"33 待回访"状态停留超过约定时长,系统 MUST 触发超期提醒
- **转包审批超时**：当转包审批在某一节点停留超时,系统 MUST 自动升级通知上级
- **回访问卷缺失**：当回访申请已发起但问卷未填写,系统 MUST 阻止审批通过
- **技术公告影响范围匹配失败**：当软件版本无法匹配到任何项目时,系统 MUST 提示"无受影响项目"并允许手动指定
- **项目成员批量变更冲突**：当批量变更项目成员时遇到并发修改,系统 MUST 提示冲突并要求刷新重试
- **合同合并拆分数据不一致**：当合并/拆分合同导致设备清单与合同关联断裂时,系统 MUST 校验并阻止操作
- **D365 接口不可用**：当推送采购订单到 D365 失败时,系统 MUST 记录失败日志并支持重试,不阻塞转包业务流程
- **文件上传中断**：当大文件上传过程中网络中断,系统 MUST 支持断点续传或重新上传
- **多数据源切换异常**：当跨数据源查询时某一数据源不可用,系统 MUST 降级提示而非整体崩溃
- **主项目提前闭环**：当主项目存在未闭环子项目时,系统 MUST 拒绝主项目闭环申请并提示未闭环子项目清单
- **子项目权限越界**：当区域团队尝试访问非本区域子项目时,系统 MUST 拒绝并记录安全日志
- **项目拆分后成员归属冲突**：当主项目拆分子项目时,系统 MUST 校验成员归属

- **项目（Project）**：项目信息主表,含项目编号、合同号、状态码、服务经理、项目经理、产品线、相关方、项目组、项目类型、业务场景模板标识等。状态机驱动生命周期。MUST 支持主子项目层级（parent_project_id 字段标识父项目）。项目级别根据逻辑自动判断,服务经理系统自动指派,项目经理手动指派。项目阶段采用双层并行模型：顶层生命周期状态机（30 已创建→31 待指派PM→32 已指派PM→40 实施中→100 已闭环,终态 20 不予跟踪,回退 36/38/42）+ "40 实施中"内嵌套 8 个交付子阶段（未开始/工前准备/编写实施方案/制定施工计划/实施部署/验收交维/超期）；交付子阶段推进采用"自动推进为主、关键节点人工触发"模式,支持受控回退；超期子阶段单独标红体现。 `[来源: 001+002]`

- **回访申请（Callback）**：回访申请主表,关联问卷结果、评价记录。MUST 归属子项目,主项目闭环前 MUST 确认全部子项目回访已完成。 `[来源: 002]`
- **维护记录（Maintenance）**：维护记录主表,关联项目主表（按 projectType）、问卷结果、交付件。MUST 归属子项目,主项目可按子项目维度汇总。 `[来源: 002]`
- **技术公告（Prob）**：技术公告主表,含修复任务、流程过程记录、进展周报、软件版本、阅读记录。用于割接已知隐患自动匹配与 ITR 故障关联。 `[来源: 001+002]`

- **项目成员（Member）**：项目成员表,记录服务经理、项目经理、安装地址、实施状态。 `[来源: 002]`
- **项目合同（Contract）**：项目合同关联表,支持合并与拆分。 `[来源: 002]`
- **用户（User）**：替代原"客户"概念,按用户维度做资产管理,属性含用户编码、名称、地址、行业、服务等级、所属单位、部门、职位、联系人；含最终用户；与 CRM 双向同步；关联角色、部门。 `[来源: 001+002]`

- **部门（Department）**：部门信息表,树形结构。 `[来源: 002]`
- **基础数据（BasicData）**：字典数据,支撑项目类型、产品线、区域等枚举。 `[来源: 002]`
- **工作流任务（Workflow Task）**：运行时任务表 + 历史任务表,驱动审批流转。 `[来源: 002]`
- **服务商（Facilitator）**：服务商/代理商信息表,承接转包业务。 `[来源: 002]`
- **操作日志（OperateLog）**：记录用户操作行为。 `[来源: 002]`
- **产品信息清单（ProductList）**：项目下产品明细,属性含产品编码、产品型号、产品描述、项目数量、发货数量、未发货数量。 `[来源: 001]`

- **割接单（CutOverOrder）**：割接管理平台核心实体,属性含割接来源、割接类型、割接等级（A/B 类）、割接对象、割接组网、操作影响、割接小组、割接计划、割接方案、操作单（准备/割接/割接后/回退）、checklist、闭环状态。 `[来源: 001]`

- **设备信息增强（DeviceEnhancement）**：设备序列号的扩展属性,含配置历史、部署风险、运行业务档案、启用功能、接口对照表、网络拓扑（自动生成）、官网版本/用户在线版本/分支版本、一码通安装地址。 `[来源: 001]`
- **客户档案（CustomerArchive）**：客户维度档案,含故障档案与服务档案。 `[来源: 001]`
- **ITR问题单（ITRTicket）**：故障处理工单,属性含来电人信息、问题描述、设备信息、发生时间、影响时长、问题级别、问题根因、解决方案、解决问题版本、Bug单号、技术公告编号、归属产线、原因大小类、当前官网版本号；关联 PMS 设备与用户。 `[来源: 001]`

- **AI排障知识库（KnowledgeBase）**：AI 排障数据基础,含产品标准手册、命令行手册、典配手册、日志手册、Mib节点手册、API手册、技术公告、已知隐患、FAQ、经典案例、排障经验；含公共 KB。 `[来源: 001]`
- **排障经验（TroubleshootingExperience）**：排障经验转换模板产出,属性含故障单号、故障现象、产品架构、触发因素、排查过程；沉淀为训练数据。 `[来源: 001]`

- **临时授权（TemporaryLicense）**：售前测试首次临时授权,设备发货后自动获取并下发。 `[来源: 001]`
- **跨系统集成点（IntegrationPoint）**：系统与外部系统的集成关系,含方向、对端系统、数据元与触发时机。 `[来源: 001]`

### 边界条件

| 边界 | 约束 |
|------|------|
| 项目状态流转 | MUST 遵循状态机:30→31→32→40→100,回退 36/38/42,终态 20。禁止非法跳转 |
| 售前状态流转 | MUST 遵循:10→31→32→33→100,终止 20。禁止非法跳转 |
| 转包审批层级 | MUST 完成全部审批节点（服务经理→通用→工程管理部→主任）方可进入合同执行 |
| 数据权限 | MUST 按角色与部门隔离,代理商仅可见本公司数据,不可见其他代理商/客户/合同/成本敏感数据；按"办事处/项目归属"维度过滤 `[来源: 001]` |
| 项目回退 | MUST 支持回退,但每次回退 MUST 记录日志并发送邮件通知；受控回退需审批 `[来源: 001]` |
| 文件上传 | MUST 支持大文件,中断后 MUST 支持断点续传或重新上传 |
| 批量导入 | MUST 校验 Excel 格式,失败行 MUST 提示具体错误 |
| 工作流超时 | MUST 支持超时升级通知,不可静默卡死 |
| 多数据源切换 | MUST 通过注解显式声明,运行时动态路由,不可跨数据源事务 |
| D365 接口 | MUST 使用 OAuth2 认证,Token 带缓存,失败 MUST 重试并记录日志 |
| 并发修改 | 关键业务表 MUST 支持乐观锁,冲突时 MUST 提示刷新重试；已提交审核文档锁定不可编辑 `[来源: 001]` |
| 主子项目状态联动 | 主项目闭环 MUST 以全部子项目闭环为前置条件 `[来源: 002][推断]` |
| 数据保留 `[来源: 001]` | 交付件/配置 Log ≥5 年,巡检/割接归档 ≥3 年,AI 训练数据脱敏长期保留；超期归档冷存储 |

## Success Criteria *(mandatory)*

- **SC-008**: Excel 批量导入支持 1000+ 行,失败行精确定位 `[来源: 002]`
- **SC-009**: 文件上传支持 100MB+ 大文件,中断后可续传 `[来源: 002]`
- **SC-010**: 多数据源切换对业务代码透明,通过注解声明即可 `[来源: 002]`
- **SC-011**: 工作流审批任务 100% 有记录,可追溯历史 `[来源: 002]`
- **SC-012**: 数据权限 100% 隔离,代理商不可见其他代理商/客户/成本敏感数据 `[来源: 002]`
- **SC-013**: 系统支持 1000 并发用户无性能 degradation `[来源: 002][推断]`

## 来源信息矛盾记录（来源: 002）

> 本章节记录来源信息之间的矛盾点。按照宪法原则,spec 仅记录矛盾不做裁决,由 plan 阶段决定取舍。spec 以老系统代码 + 知识库为现状基线,以系统设计文档为目标设计参考。

### 矛盾 1: 技术栈定位

| 维度 | 老系统代码 + 知识库（现状基线） | 系统设计文档 V1.0（目标设计） |
|------|-------------------------------|-------------------------------|
| 技术栈 | Struts2 2.5.30 + iBATIS 2 + Activiti 5.23.0 + Shiro+CAS + JDK 1.8 | Spring Boot 3.2.x + MyBatis-Plus + Flowable 7.x + Vue 3 + JDK 17 |
| 数据源 | 9 个数据源（多数据库类型） | MySQL 8.0 单库主从 + Redis + ES |
| 部署 | 传统 WAR 部署 | 容器化（Docker/K8s） |

**裁决**：新系统 MUST 选用现代技术栈,但 MUST 保留老系统业务流程语义。spec 以老系统为业务基线,技术栈选型在 plan 阶段参照系统设计文档决定。

### 矛盾 2: 业务模块划分

spec（以老系统为基线）与系统设计文档（新设计）在模块划分上存在差异。spec 独有：售前、转包、闭环回访、维保、技术公告、周报文件；系统设计文档独有：设备资产、资源调度、代理商管理、交付管理、验收管理、财务核算。**裁决**：不裁决模块合并细节。新系统 MUST 按业务域聚合组织模块（003 澄清）：以"项目交付生命周期"为主线（立项/工前/计划/方案/部署/验收/割接/归档），002 老模块作为子能力嵌入对应阶段（转包嵌入"部署"、回访嵌入"验收"、维保嵌入"归档"、售前作为独立业务场景复用生命周期），横切模块（系统管理/工作流/报表/集成/安全/数据持久化）独立。具体模块边界与拆分在 plan 阶段细化。

### 矛盾 3: 认证方式

001 澄清为 LDAP/AD 统一认证,002 记录老系统为 CAS 单点登录。**裁决**：新系统采用 LDAP/AD 统一认证（001 澄清）,CAS 作为老系统现状基线保留记录。

## Assumptions

- **目标用户**：原厂内部人员（管理员、服务经理、项目经理、工程管理部、主任）、代理商/服务商、客户（通过 H5 入口） `[来源: 002]`
- **网络环境**：内部用户稳定内网,代理商/移动端用户稳定互联网 `[来源: 002]`

- **历史数据**：老系统（dppms_d365 库）仅核心业务表需迁移（项目/售前/转包/回访/维保 + 基础数据 + 用户/部门）,非核心表（临时表/日志表/冗余表）不迁移 `[来源: 002]`

- **CAS 单点登录**：老系统沿用 CAS 认证体系；新系统采用 LDAP/AD 统一认证 `[来源: 001+002]`
- **多数据源**：老系统的多数据源架构需在新系统中保留,不可合并为单库 `[来源: 002]`
- **工作流引擎**：新系统 MUST 保留老系统业务流程语义（状态机、审批节点、角色指派）,但 MUST NOT 复用 Activiti 5.x 引擎与原 BPMN 文件；MUST 选用现代工作流引擎重新实现流程定义 `[来源: 002]`

- **集成方式**：与 D365 的 OAuth2 + REST API 集成模式需保留 `[来源: 002]`
- **SPMS 关联**：新 PMS 与 SPMS MUST 解耦,不共享数据库,备件相关操作通过标准 API 接口集成 `[来源: 002]`

## 范围边界

### 模块维度说明
